# Gleann REST API Reference

Gleann exposes a REST API when running in server mode (`gleann serve`). The API provides endpoints for index management, semantic search, RAG-based Q&A, and code graph queries.

> **Address note:** `gleann serve` binds `127.0.0.1:8081` by default. Every example in this document assumes the Quick Start command `gleann serve --port 8080`, i.e. `http://localhost:8080`. If you start the server without `--port`/`--addr`, use `http://127.0.0.1:8081` instead.

## Quick Start

```bash
# Start the server
gleann serve --port 8080

# Open API documentation in browser
open http://localhost:8080/api/docs

# Download the OpenAPI spec
curl http://localhost:8080/api/openapi.json
```

## Import into Postman / Swagger UI

### Where the spec lives

The OpenAPI 3.0 specification is generated by the server itself:
`internal/server/openapi.go` assembles it from the route tables in
`internal/server/openapi_paths*.go` and the schemas in
`internal/server/openapi_schemas.go`. There is no checked-in static JSON
file; a running server serves the spec at **`GET /api/openapi.json`** and an
embedded Swagger UI at **`GET /api/docs`**. `internal/doccheck` fails the
build if a route registered by the server is missing from the specification
(or the spec promises a route the server does not answer), so the served
JSON is always the file to import into an API client.

To import offline, save a copy first:

```bash
curl http://localhost:8080/api/openapi.json -o gleann-openapi.json
```

### Postman

1. **File → Import → Link** and enter
   `http://localhost:8080/api/openapi.json` (or drag in the saved
   `gleann-openapi.json`). Use the port your `gleann serve` runs on.
2. Open the imported collection's **Authorization** tab, set the type to
   **Bearer Token**, and paste a token (see below). The spec declares
   `bearerAuth` once at the top level, so every request inherits it.

### Swagger UI

- The server ships one: open **`GET /api/docs`**
  (`http://localhost:8080/api/docs`) in a browser; it loads
  `/api/openapi.json` automatically.
- Or point any Swagger UI (e.g. `swagger-ui-dist`, or the online editor at
  `https://editor.swagger.io`) at the served URL or the saved
  `gleann-openapi.json` file.
- Click **Authorize** and enter the token value only (Swagger UI adds the
  `Bearer` scheme itself).

### Setting the bearer token

```bash
gleann token create ci --scope query     # read-only: search, ask, /v1, A2A, GET routes (indexes, graph, memory blocks)
gleann token create deploy --scope admin # writes: builds, config, memory writes
gleann token show                        # the admin token created by gleann serve
```

Tokens are shown once at creation; `gleann serve` also writes an admin token
to `~/.gleann/auth/admin.token` on first start. For `curl`, export it once:
`export GLEANN_API_TOKEN=$(gleann token show)` (see [Authentication](#authentication)).

Both documentation endpoints are public. The spec declares `bearerAuth` once
at the top level, and the four public routes (`GET /health`,
`GET /.well-known/agent-card.json`, `GET /api/docs`, `GET /api/openapi.json`)
override it with an empty `security` list.
`TestSpecSecurityMatchesPublicRoutes` fails the build when a route the server
serves without a token inherits `bearerAuth` in the spec (or a protected route
is marked public). The embedded web UI's static files are also served without
a token, but they are deliberately outside the spec.

|--------|------|-------------|
| GET | `/api/indexes` | List all indexes |

### OpenAI-Compatible Proxy

Use gleann indexes as if they were OpenAI models. Compatible with any tool that speaks the OpenAI chat completions API.

| Method | Path | Description |
|--------|------|-------------|
| GET | `/v1/models` | List indexes as OpenAI-compatible model objects |
| POST | `/v1/chat/completions` | Chat completions with automatic RAG injection |
| POST | `/stop` | Forwarded to the LLM server in pass-through mode (below); `404` otherwise |

**Model naming**: `"gleann/<index-name>"` for RAG-augmented answers, `"gleann/"` for pure LLM pass-through.

**Custom headers**: `X-Gleann-Top-K` (RAG result count), `X-Gleann-Min-Score` (score threshold), `X-Gleann-Hybrid-Alpha` (vector against lexical weight, a number from 0 to 1; `0` = lexical (BM25) search only, no query embedding; a value outside the range or not a number is ignored, like the other two; works in both proxy modes and, with several indexes, in the cross-index ranking).

**Pass-through mode** (`proxy_mode: "passthrough"` in the config, or `GLEANN_PROXY_MODE=passthrough`): the request
goes to the configured OpenAI-compatible server unchanged (every field, e.g. `chat_template_kwargs`), and its reply
comes back byte for byte with its status code, so clients keep whatever their LLM server streams (reasoning,
timing metrics, errors). The only change is the retrieved context, which is appended to the first system message
(or added as one), and the model name, which becomes `llm_model` when it named indexes. The passages follow an intro
sentence that is configurable (`proxy_context_intro` / `GLEANN_PROXY_CONTEXT_INTRO`, English by default) and always
ends with the instruction to answer in the language of the user's question. Indexes can also be given
in an `X-Gleann-Index` header (`docs,code`, `@tag`). The reply carries `X-Gleann-Sources`, the passages' sources in
order as a percent-encoded JSON list of `{index, source, score}`. With several indexes, one that cannot be loaded
or searched (for example an index in the old store format) is left out and logged, and the reply lists it in
`X-Gleann-Skipped-Indexes`, a percent-encoded JSON list of `{index, reason}`. `POST /stop` is forwarded to the LLM
server in this mode. Optional headers in this mode:

| Header | Effect |
|---|---|
| `X-Gleann-Context: user` | Put the passages into the last user message (before its text) instead of the first system message. The conversation before it then stays the same from turn to turn, so the LLM server can reuse its prompt cache. |
| `X-Gleann-Max-Context-Chars: N` | Keep the best passages up to N characters (at least one passage). |
| `X-Gleann-Hybrid-Alpha: A` | Vector/lexical weight for this request (0 to 1, `0` = lexical only); see the custom headers above. |
| `X-Gleann-Cover: true` | Several indexes: an index whose best passage is close to the overall best keeps that passage in the context, replacing the lowest-ranked extra passage of another index. The context keeps its top-k and `X-Gleann-Max-Context-Chars` size, no index loses its only passage, and the order of the others stays. "Close" means a vector distance at most the overall best plus a margin, or a BM25 score at least a share of the overall best and above a floor (vector test only when the search weighs vectors, lexical only when it weighs BM25). Config `proxy_cover` turns it on by default; `false` turns it off for a request. |
| `X-Gleann-Cover-Margin: M`, `-Share: S`, `-Floor: F` | Thresholds of "close" for this request: vector distance margin (default 0.1), BM25 share 0 to 1 (default 0.6) and BM25 floor (default 1.0). Defaults are starting points, not calibrated to a model: distance and BM25 scales depend on your embedding model and corpus. Config: `proxy_cover_margin`, `proxy_cover_share`, `proxy_cover_floor`. Invalid values are ignored. |
| `X-Gleann-Rerank: true` or a model | Rerank this request with the configured reranker, or with the named model. |
| `X-Gleann-Rerank-Pool: N` | Candidates sent to the reranker. |

With several indexes, the passages are ranked together and the best top-k are kept, whichever index they come
from.

### A2A Protocol (Agent-to-Agent)

Google's Agent-to-Agent protocol for agent discovery and inter-agent communication. Enabled by default; set `GLEANN_A2A_ENABLED=false` to disable.

| Method | Path | Description |
|--------|------|-------------|
| GET | `/.well-known/agent-card.json` | A2A Agent Card (discovery) |
| POST | `/a2a/v1/message:send` | Send a message to an A2A skill |
| GET | `/a2a/v1/tasks/{id}` | Get task status by ID |

**Built-in skills**: `semantic-search`, `ask-rag`, `code-analysis`, `memory-management`.

A2A routes accept a query token, but privileged skill operations require an **admin** token:
storing memory blocks (`memory-management`) and analyzing a server-local file path
(`multimodal-analyze`). With a query token those tasks fail with an admin-scope message;
memory recall/search and file attachments stay available. See [a2a.md](a2a.md#authentication-and-scopes).

### Unified Memory API

Orchestrates all memory layers (block storage, knowledge graph, vector search) through a single interface. Simplifies agent integration by eliminating the need to call individual memory APIs.

| Method | Path | Description |
|--------|------|-------------|
| POST | `/api/memory/ingest` | Store facts + relationships across memory layers |
| POST | `/api/memory/recall` | Query all memory layers in parallel |

#### Ingest Request Fields

| Field | Type | Description |
|-------|------|-------------|
| `facts[].content` | string | **Required.** The fact text to store |
| `facts[].tags` | string[] | Searchable tags |
| `facts[].tier` | string | `short` (default), `medium`, or `long` |
| `facts[].metadata` | object | Arbitrary key-value metadata (e.g. `{"source_file": "auth.go"}`) |
| `facts[].expires_in` | string | TTL as Go duration (`1h`, `7d`, `2w`) |
| `facts[].char_limit` | int | Per-block character limit |
| `relationships[].from` | string | Source entity ID |
| `relationships[].to` | string | Target entity ID |
| `relationships[].relation` | string | Relation type (e.g. `DEPENDS_ON`, `IMPLEMENTS`) |
| `relationships[].weight` | float | Edge importance (default: 1.0) |
| `relationships[].attributes` | object | Edge metadata |
| `scope` | string | Isolate facts to a conversation/agent |

#### Recall Request Fields

| Field | Type | Description |
|-------|------|-------------|
| `query` | string | **Required.** Search text |
| `index` | string | Index namespace for the `vector` and `graph` layers; must be accessible or those layers are omitted |
| `project` | string | Project scoping shorthand: sets block scope to `project:{name}` and targets the matching index |
| `target` | string | Alias for `project`; pins recall to a specific target index and scope |
| `layers` | string[] | `blocks`, `graph`, `vector` (default: all) |
| `top_k` | int | Max results per layer (default: 5; graph hard cap: 256 nodes and 512 edges) |
| `tier` | string | Filter blocks by tier |
| `tags` | string[] | Filter blocks by tags (AND logic) |
| `after` | string | Filter blocks created after (RFC3339 or duration like `24h`, `7d`) |
| `before` | string | Filter blocks created before |
| `relations` | string[] | Exact, case-insensitive graph relation-type filter; empty/whitespace entries are ignored, and a filter left empty allows every relation type |
| `scope` | string | Filter blocks by scope |
| `depth` | int | Graph traversal hops (default: 2; hard cap: 10; values ≤ 0 mean the default) |
| `format` | string | `json` (default) or `context` (LLM-ready XML) |

#### Unified Memory Examples

```bash
# Store a fact with metadata and TTL
curl -X POST http://localhost:8080/api/memory/ingest \
  -H 'Content-Type: application/json' \
  -d '{
    "facts": [{
      "content": "Auth service uses JWT tokens with RS256 signing",
      "tags": ["auth", "security", "jwt"],
      "metadata": {"source_file": "auth/jwt.go", "confidence": "high"},
      "tier": "long",
      "expires_in": "90d"
    }],
    "relationships": [{
      "from": "AuthService",
      "to": "JWTValidator",
      "relation": "DEPENDS_ON",
      "weight": 0.9
    }]
  }'

# Project-scoped ingest (sets scope="project:myapp" + default index)
curl -X POST http://localhost:8080/api/memory/ingest \
  -H 'Content-Type: application/json' \
  -d '{
    "project": "myapp",
    "facts": [{"content": "The API uses rate limiting at 100 req/s"}],
    "relationships": [{"from": "Gateway", "to": "RateLimiter", "relation": "USES"}]
  }'

# Recall facts from the last 7 days, filtered by tag
curl -X POST http://localhost:8080/api/memory/recall \
  -H 'Content-Type: application/json' \
  -d '{
    "query": "authentication",
    "layers": ["blocks"],
    "tags": ["security"],
    "after": "7d",
    "tier": "long"
  }'

# Project-scoped recall (searches blocks with scope + vector/graph in index)
curl -X POST http://localhost:8080/api/memory/recall \
  -H 'Content-Type: application/json' \
  -d '{
    "project": "myapp",
    "query": "rate limiting",
    "format": "context"
  }'

# Graph-layer recall: every whitespace token in the query must substring-match
# an entity ID, type, or content (AND of ORs, case-insensitive with Unicode
# folding), or a relation type. top_k bounds returned entities (default 5, hard
# cap 256); edges are capped at 2x entities (hard cap 512) and depth at 10 hops
# (default 2). When top_k >= 2 and depth > 0, about half the node budget is
# reserved for neighbours: the seeds' own incoming/outgoing relations are
# expanded first, remaining seed slots are backfilled, and only then are
# relation-type matches admitted (and only when both endpoints fit the node
# budget, since an edge whose endpoint is over budget would be dropped).
# relations is an exact case-insensitive type filter; empty entries are ignored.
# Private or unknown indexes return no graph data.
curl -X POST http://localhost:8080/api/memory/recall \
  -H 'Content-Type: application/json' \
  -d '{
    "index": "myapp",
    "query": "auth",
    "layers": ["graph"],
    "top_k": 10,
    "depth": 2
  }'

# Full multi-layer recall in LLM-ready format
curl -X POST http://localhost:8080/api/memory/recall \
  -H 'Content-Type: application/json' \
  -d '{
    "query": "how does auth work",
    "format": "context",
    "top_k": 10
  }'
# Returns XML with <facts>, <relationships>, <relevant_documents>, and
# <entities> when a graph layer has matching nodes but no surviving edges.
```

## Examples

### Search

```bash
curl -X POST http://localhost:8080/api/indexes/my-code/search \
  -H 'Content-Type: application/json' \
  -d '{
    "query": "how does authentication work",
    "top_k": 5,
    "hybrid_alpha": 0.7,
    "graph_context": true
  }'
```

`hybrid_alpha` weighs the vector leg against the lexical (BM25) leg: `1` is
vectors only, `0` is lexical only (the query is not embedded), and an absent
field keeps the configured weight. A value outside `[0, 1]` is `400`. The same
holds for `POST /api/search`.

The response carries `results`, `count` and `query_ms`. When the index is known
to be damaged (passage IDs with gaps, left by versions before v1.8.6), it also
carries `warnings`, a list of messages that name the problem and the fix
(`gleann index repair <name>`); results from such an index may be wrong or
incomplete. The field is absent for a healthy index.

`metadata_filters` narrows results to passages whose metadata matches the
conditions (`filter_logic`: `and`, the default, or `or`). Each condition is
`{"field": ..., "operator": ..., "value": ...}`; operators are `eq`, `ne`,
`gt`, `gte`, `lt`, `lte`, `in`, `nin`, `contains`, `startswith`, `endswith`,
`exists`; a condition with another key (`op` is not `operator`), a missing field or a missing or unknown operator answers `400`. Fields understand the `type`/`kind` and `source`/`file` aliases and
derive `ext` from the file path. Filters are applied during retrieval, not
after it: a selective filter still returns `top_k` results when that many
passages match — the candidate pool widens until k pass (sized from the
observed pass rate), capped at 4096 candidates. When the filter is estimated
to match only a small fraction of the index (at most a fifth, and at most
12,000 passages), or when the loop stops at that cap with fewer than k results, the
index pre-selects the matching IDs in SQL (reading `id`/`vec_slot`/`source`/
`kind`/`meta`, never passage text, capped at 50,000 rows) and scores just
those. Backends that store the raw vectors (HNSW and DiskANN, loaded in RAM
or memory-mapped) score the pre-selected set by exact vector distance, so a
selective filter bypasses the approximate search entirely. A filter nothing
matches returns 0. A passage's score is the same with and without a filter
that keeps it, and the pre-selected path applies the same `min_score`, `kind`
and ranking boosts as the main path.

```bash
curl -N -X POST http://localhost:8080/api/indexes/my-code/ask \
  -H 'Content-Type: application/json' \
  -d '{

    "stream": true
```

Or use the query parameter:

```bash

  -H 'Content-Type: application/json' \
  -d '{"question": "Explain the authentication flow"}'
```

**Response format** (`Content-Type: text/event-stream`):

```
data: {"token":"The"}

data: {"token":" authentication"}

data: {"token":" flow"}

data: {"token":" works by..."}

data: [DONE]
```

Each `data:` line contains a JSON object with a `token` field. The stream ends with `data: [DONE]`. If an error occurs mid-stream, it sends `data: {"error": "..."}` before `[DONE]`.

**JavaScript example**:

```javascript
const response = await fetch('/api/indexes/my-code/ask', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ question: 'How does auth work?', stream: true })
});

const reader = response.body.getReader();
const decoder = new TextDecoder();

while (true) {
  const { done, value } = await reader.read();
  if (done) break;
  const text = decoder.decode(value);
  for (const line of text.split('\n')) {
    if (line.startsWith('data: ') && line !== 'data: [DONE]') {
      const { token } = JSON.parse(line.slice(6));
      process.stdout.write(token); // or append to UI
    }
  }
}
```

### Update Index

Remove the passages that came from some sources and/or add new items:

```bash
curl -X POST http://localhost:8080/api/indexes/test-index/update \
  -H 'Content-Type: application/json' \
  -d '{
    "sources": ["notes.md"],
    "items": [{"text": "Revised notes", "metadata": {"source": "notes.md"}}]
  }'
```

The response says how the update was applied and what it cost:

```json
{"status": "ok", "index": "test-index", "updated_sources": ["notes.md"], "items_count": 1,
 "duration_ms": 41, "mode": "compact", "passages": 3, "removed": 1, "embedded_texts": 3}
```

`mode` is `in-place` when new passages were appended to the existing vector
index (only the new texts are embedded), `compact` when passages were removed
and the index was rebuilt from the remaining ones (every remaining passage is
embedded again; the embedding cache makes this cheap when the texts are
unchanged), `emptied` when the last passage was removed (the vector index is
deleted and the next add starts it afresh) and `noop` when there was nothing to
do. Removing passages never edits the vector index in place: vectors are
addressed by position, so doing so would attach them to the wrong passages.

## Authentication

> The `curl` examples in this file leave out the header for brevity. Add `-H "Authorization: Bearer $GLEANN_API_TOKEN"` (export the token with `export GLEANN_API_TOKEN=$(gleann token show)`), unless the server runs with `auth: off`.

Every route except `GET /health`, `GET /.well-known/agent-card.json`, `GET /api/docs`,
`GET /api/openapi.json` and the static web UI requires a bearer token:

```bash
curl -H "Authorization: Bearer $GLEANN_API_TOKEN" http://127.0.0.1:8081/api/indexes
```

- `gleann serve` creates an **admin** token on first start (`~/.gleann/auth/admin.token`, mode 0600) and
  prints a web UI URL with `?token=`; the server turns it into an `HttpOnly; SameSite=Strict` cookie.
- `gleann token create <name> [--scope query|admin]`, `list`, `revoke`, `rotate`, `show`.
  Tokens are shown once; only SHA-256 hashes are stored (`~/.gleann/auth/tokens.json`).
- Scopes: `query` = search, ask, `/v1/*`, read-only `/a2a/*` skills, read-only index/graph/memory/conversation routes;
  `admin` = everything else (config, build, delete, plugins, memory writes — including A2A memory
  writes and A2A analysis of server-local file paths, ...).
- The CLI and stdio MCP memory tools read `GLEANN_API_TOKEN` or `~/.gleann/auth/admin.token` automatically.
- OpenAI-compatible clients: set `api_key` to a token. A2A clients: the agent card advertises `gleannBearer`.
- `401` = missing/invalid token, `403` = scope too low, wrong `Host`, or cross-origin cookie request.
- `auth: "off"` (config) / `GLEANN_AUTH=off` disables authentication and is refused unless the server binds a loopback address.

The server binds `127.0.0.1:8081` by default; `--port N` also binds loopback. Use `--addr :8081` (or `0.0.0.0:...`)
to listen on all interfaces. On a loopback bind the `Host` header must be a loopback name
(add others with `GLEANN_ALLOWED_HOSTS`).

## CORS

No CORS headers are sent by default (the web UI is same-origin). To allow a browser app on another origin, list it in
`cors_origins` (config) or `GLEANN_CORS_ORIGINS` (comma separated); allowed origins get
`Access-Control-Allow-Origin: <origin>` and `Access-Control-Allow-Methods: GET, POST, PUT, PATCH, DELETE, OPTIONS`.
Cross-origin calls still need a bearer token.

## Error Responses

All errors return JSON with a single `error` field:

```json
{
  "error": "index \"foo\" not found: open .../foo/meta.json: no such file or directory"
}
```

Common HTTP status codes:

| Code | Meaning |
|------|---------|
| 200 | Success |
| 400 | Bad request (missing required fields) |
| 403 | Scope too low, or a client-supplied path (`index-path`, `update` `docs_root`, `watch` `dir`, graph `docs_dir`) is outside `allowed_roots` (see below) |
| 404 | Index or graph not found. `GLEANN_TAGS` restricts every index route, reads and writes (build, update, index-path, watch, upload, storage, delete, graph, memory, multi-index search, the OpenAI proxy); a missing (or unreadable) index looks like a forbidden one to a restricted client: the same `403`, so index names cannot be probed. Exception: with `GLEANN_TAGS` set, `build` creates a new index when its `tags` include an allowed tag (stored with the index); `upload` cannot carry tags and so cannot create one. Under `GLEANN_TAGS`, `build`, `PATCH` and `index-path` accept only tags inside the allowed set (`build` and `PATCH` also at least one of them; `403` otherwise); `index-path` cannot create an index under `GLEANN_TAGS` |
| 429 | Rate limit exceeded (per-IP token bucket; see `GLEANN_RATE_LIMIT`) — includes `Retry-After: 1` header |
| 500 | Internal server error (also an index that exists but cannot be loaded: corrupt or unreadable) |
| 503 | Feature unavailable |
| 504 | Gateway timeout — request exceeded its deadline (see `GLEANN_TIMEOUT_*_S` env vars) |

## Allowed Paths

Routes that make the server read or index a directory named by the client (`index-path`, `update` with
`docs_root`, `watch` with `dir`, `POST /api/graph/{name}/index` with `docs_dir`) accept only paths inside the
directories listed in `allowed_roots` (config) or `GLEANN_ALLOWED_ROOTS` (path-list separated); with neither set,
that is the server user's home directory. Paths are cleaned and symlinks resolved first, so `..` and symlinks
cannot leave a root. Anything else gets `403`:

```json
{ "error": "path \"/etc\" is not inside the directories this server may read; add its parent to allowed_roots in config.json (or GLEANN_ALLOWED_ROOTS)" }
```

`gleann index build` on the command line is not restricted. The MCP tools `gleann_read` and
`gleann_read_full_document` read only inside the index's source directory, and `gleann_sync` holds an explicit
`docs_dir` to the same roots (plus the index's source directory and the working directory).

## Rate Limiting

The server applies per-IP token-bucket rate limiting (default: 60 req/s sustained, 120 burst). The `/health` and `/metrics` endpoints are exempt. Configure via `GLEANN_RATE_LIMIT` and `GLEANN_RATE_BURST` environment variables.

## Request Timeouts

Each endpoint has a context deadline based on its path:

| Endpoint pattern | Default timeout | Env var |
|-----------------|----------------|---------|
| `*/ask`, `/v1/chat/completions` | 5 minutes | `GLEANN_TIMEOUT_ASK_S` |
| `*/search` | 30 seconds | `GLEANN_TIMEOUT_SEARCH_S` |
| `*/build` | 10 minutes | `GLEANN_TIMEOUT_BUILD_S` |
| All others | 60 seconds | `GLEANN_TIMEOUT_DEFAULT_S` |

SSE streaming endpoints (`?stream=true` or `Accept: text/event-stream`) bypass the timeout middleware; they rely on client disconnect detection instead.

sentinel is rejected with `403`, as is any header/body target mismatch after
normalization.

### List all blocks

The scope filter resolves from `?scope=` / `?target=` / the `X-Gleann-Target`
header (normalized; mismatch returns `403`). A sentinel (`all` / `*`,
case-insensitive) selects **all scopes** when unrestricted — the same
behaviour whether it arrives in the query string or the header; against a
restricted target the sentinel is rejected with `403`. With no scope filter
every block is listed.

```bash
# All tiers
curl http://localhost:8080/api/blocks

# Only long-term memories
curl http://localhost:8080/api/blocks?tier=long

# Scoped to a conversation (global + conversation-specific)

# Explicit all-scope sentinel (equivalent to no filter when unrestricted)
curl 'http://localhost:8080/api/blocks?scope=all'
curl -H 'X-Gleann-Target: all' http://localhost:8080/api/blocks
```

### Search blocks

Same scope resolution as listing: `?scope=` / `?target=` / `X-Gleann-Target`,

```bash
curl 'http://localhost:8080/api/blocks/context?command=go%20test&scope=github.com/org/repo'
```

### Record a command failure

Records a failure memory (command + error + fix) so future sessions surface it
via the task-scoped context instead of repeating the mistake. **Admin scope
required.** Recording the same failure again reinforces the existing block
(`confirms` increments) rather than adding a duplicate.

The target scope resolves from `?scope=` / `?target=` / the `X-Gleann-Target`
header and must agree with any `scope` in the body **after normalization** (a
mismatch returns `403`; `repo-a` and `repo-a/` are the same target). When
`scope` is empty but `repo` is set, the scope defaults to `repo`. A body or
query `scope` of `all` / `*` records a **global** block when unrestricted
(never a literal scope named `all`); against a restricted target the sentinel
is rejected with `403`. A sentinel `repo` is treated the same way: it never
creates a literal `all` scope.

Returns the saved failure block: **`201 Created`** on first recording, **`200 OK`**
when the same failure is confirmed again (`confirms > 1`).

```bash
curl -X POST http://localhost:8080/api/blocks/failures \
  -H 'Content-Type: application/json' \
  -H 'Authorization: Bearer <admin-token>' \
  -d '{
    "command": "go test ./pkg/memory/",
    "error": "undefined: SomeUndefinedVar",
    "fix": "changed SomeUndefinedVar to SomeDefinedVar",
    "paths": ["pkg/memory/test.go"],
    "symbols": ["github.com/org/repo/pkg/memory.TestExample"],
    "scope": "github.com/org/repo"
  }'

# Scope via the target header instead of the body
curl -X POST http://localhost:8080/api/blocks/failures \
  -H 'Content-Type: application/json' \
  -H 'X-Gleann-Target: conv-abc123' \
  -d '{"command":"make lint","error":"SA1019","fix":"use the new API"}'
```

### List recorded failures

Returns the failure blocks visible to a scope (global + the scope and its
ancestors). **Requires query auth scope (`ScopeQuery`).** The target scope
filter is optional: it resolves from `?scope=` / `?target=` / the
`X-Gleann-Target` header (normalized, so `repo-a`, `repo-a/` and `/repo-a` name
the same scope), defaults to the token/header target, and lists **all scopes**
when omitted. `?scope=all` / `?scope=*` explicitly selects all scopes when
unrestricted; against a restricted `X-Gleann-Target` / `?target=` the sentinel
is rejected with `403`, as is any header/query target mismatch (same rule as
the POST above). With no `command` / `paths` / `symbols` filter it lists every
failure in the scope; otherwise it returns only the failures matching the task
query. `paths`/`symbols` are comma-separated; `path` and `symbol` are repeatable
singular aliases. The response is `{"failures": [...], "count": N}` (`failures`
is always an array).

```bash
# All failures (every scope)
curl http://localhost:8080/api/blocks/failures

# Explicit all-scope sentinel (equivalent when unrestricted)
curl 'http://localhost:8080/api/blocks/failures?scope=all'

# Failures visible to a repository scope
curl 'http://localhost:8080/api/blocks/failures?scope=github.com/org/repo'

# Scope via ?target= or the target header (must agree with ?scope=)
curl 'http://localhost:8080/api/blocks/failures?target=github.com/org/repo'
curl -H 'X-Gleann-Target: github.com/org/repo' http://localhost:8080/api/blocks/failures

# Failures matching a command
curl 'http://localhost:8080/api/blocks/failures?command=go%20test'

# Failures matching file paths (comma-separated or repeated)
curl 'http://localhost:8080/api/blocks/failures?paths=pkg/a.go,pkg/b.go'
curl 'http://localhost:8080/api/blocks/failures?path=pkg/a.go&path=pkg/b.go'

# Failures matching symbols (FQN or trailing segment)
curl 'http://localhost:8080/api/blocks/failures?symbols=pkg.Foo'
curl 'http://localhost:8080/api/blocks/failures?symbol=TestExample'
```

## Examples: OpenAI-Compatible Proxy

Use any OpenAI-compatible client with gleann as the backend:

```bash
# RAG-augmented: model = "gleann/<index-name>"
curl -X POST http://localhost:8080/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "gleann/my-code",
    "messages": [{"role": "user", "content": "How does auth work?"}],
    "stream": false
  }'

# Custom RAG parameters via headers
curl -X POST http://localhost:8080/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -H 'X-Gleann-Top-K: 15' \
  -d '{
    "model": "gleann/my-docs",
    "messages": [{"role": "user", "content": "Summarize the architecture"}]
  }'

# List available indexes as OpenAI models
curl http://localhost:8080/v1/models
```

**Python (OpenAI SDK)**:
```python
from openai import OpenAI

client = OpenAI(base_url="http://localhost:8080/v1", api_key=os.environ["GLEANN_API_TOKEN"])  # a gleann token; "unused" gets 401
response = client.chat.completions.create(
    model="gleann/my-code",
    messages=[{"role": "user", "content": "Explain the auth flow"}],
)
print(response.choices[0].message.content)
```
