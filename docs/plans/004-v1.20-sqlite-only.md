## 1. Decision

The maintainer decided on 2026-11-17:

1. **Remove Kùzu.** Measured at 1M edges on the same synthetic graph (cores 0-3), the SQLite code graph answers every query with identical results (0 parity mismatches) and is faster on every query and update. Kùzu is better only on full load and disk; that trade is accepted.

   | 1M edges, p50 | Kùzu | SQLite |
   |---|---|---|
   | callers, depth 3 | 125 ms | 1.6 ms |
   | impact, depth 3 | 298 ms | 1.7 ms |
   | symbol search | 34.5 ms | 2.2 ms |
   | shortest path | 0.43 s, found no path | 5.6 ms |
   | one-file update | 865 ms | 140 ms |
   | full load | **2.3 s** | 7.4 s |
   | disk | **52 MiB** | 182 MiB |

   Further reasons: Kùzu needs CGo and a shipped shared library (`libkuzu`), so the default `go install` build and Windows had no code graph; two graph engines meant two write paths, tag pairs and raw-Cypher endpoints; the graph and the passages lived in different stores with no common transaction.
2. **Store format 2 becomes the only index format**, with the persisted FTS5 lexical index and its options (`and,df=0.2`) as the only lexical path.
3. **No backward compatibility for index data.** Indexes are derived data and can be rebuilt from their sources. Format-1 indexes (bbolt passages, in-memory BM25, `<name>_graph` Kùzu) are not read by v1.20.0 search, sync or graph code.
4. **User data that cannot be rebuilt is carried over once:** the memory database (`memory.db` bbolt to `memory.sqlite`, already in place) and memory entities stored in old `<name>_memory` Kùzu directories (new: one-shot export/import, section 4).
5. **Keep a pluggable graph-database benchmark** so another database can be evaluated later against the SQLite graph (section 5).

## 2. What changes for users (upgrade notes, to become `docs/releases/v1.20.0.md`)

| Before (v1.9.x) | v1.20.0 |
|---|---|
| Default index: bbolt passages + in-memory BM25; `GLEANN_STORE_FORMAT=2` opt-in | Every index is one SQLite database `<IndexDir>/<name>/<name>.db` (passages, FTS5 lexical index, manifest, code graph, document graph) |
| Code graph only in `-tags treesitter` builds, in `<name>_graph` (Kùzu) | Code graph in every build, including `go install` and Windows; `-tags treesitter` adds tree-sitter parsers (CALLS for non-Go languages) |
| `GLEANN_STORE_FORMAT`, `GLEANN_LEXICAL`, `GLEANN_LEXICAL_OPTS` | Removed (format 2 and FTS5 with AND-first + df cut are fixed); an unknown value is ignored with a one-line notice |
| `POST /api/graph/{name}/query` with `type: "cypher"`, UI "Raw Cypher" | Removed (400 with a message); typed queries remain |
| `libkuzu` shipped with full builds | Not shipped |

**Upgrading an existing index:** `gleann index migrate <name>|--all` converts a format-1 index in place without re-embedding (vectors are reused) and then builds the code graph when the index had one (`--graph`). This command is the only code that still reads format 1; it is kept for v1.20.x and removed in v1.21. Any other command on a format-1 index stops with: `index X uses the old store format; run: gleann index migrate X`. `gleann index rebuild X` also works (re-embeds).

**Old directories** (`<name>_graph`, `<name>_graph_file_hashes.db`, `<name>.passages.db`, `<name>.lex.db`, `<name>_memory`) are never deleted implicitly. `index migrate --cleanup` deletes the converted index's old files and prints each path; `index remove` removes everything of an index, as today; `gleann doctor` lists leftovers.

## 4. Memory entities in old Kùzu directories

v1.9.x stored entities injected through `inject_knowledge_graph` in `<IndexDir>/<name>_memory` (Kùzu). They cannot be rebuilt from sources. Plan:

0. **Where the data is:** v1.9.0 pins go-kuzu v0.11.3, which stores a database as one file plus `.wal`/`.shadow` (not a directory); stores created before `Entity_Archive` existed lack that table. Detection (`internal/server/memory_handler.go`, `internal/mcp/memory_tools.go`) handles file or directory and its message is corrected (today it points to a non-existent migrate path).
1. **Export tool in its own module** `tools/kuzu-memory-export` (own `go.mod` with the Kùzu binding, CGo; not part of the main module, not in CI's default jobs). It opens each `<name>_memory` directory read-only, reads entities, relations and the archive, and writes one JSON file per namespace in its own format `{entities, relations, archive}` with every attribute and timestamp as stored (`GraphInjectionPayload` has no archive and `InjectEntities` re-archives and re-stamps, so it is not used). Release assets include prebuilt binaries for linux/amd64, linux/arm64 and darwin/arm64 (Kùzu has no Windows build in gleann today).
2. **Import in the main binary**: `gleann memory import-graph <file.json>|<dir>` (and the existing `POST /api/memory/{name}/inject`) loads it into `memory.sqlite` row by row with `INSERT OR IGNORE`, keeps timestamps, records an import marker in `memory_meta`; a second run changes nothing (tested on the `entity_archive` row count).
3. **Detection**: when gleann finds `<name>_memory` without a matching import marker, it logs once per process the exact two commands to run; `gleann doctor` lists them.
4. Proof: fixtures written by v1.9.0 (current schema, pre-archive schema, a store with a leftover `.wal`) → export → import → `traverse_knowledge_graph` returns the same entities and relations as v1.9.0 did (golden recorded before A3).

Removed in v1.21 together with the format-1 reader.

## 5. Pluggable graph-database benchmark

A nested module `bench/graphdb` (module path `github.com/tevfik/gleann/bench/graphdb`, own `go.mod` with `replace … => ../..`) so it can use gleann's `internal/graphstore` and fixture while candidate databases add dependencies only to the nested module. It defines a `Backend` interface (bulk load, one-file delta, remove file, callers/callees/impact by depth, symbol search, shortest path, stats, disk bytes, close), a runner (sizes, query counts, cores 0-3 advice) and a report (markdown + JSON: load, p50/p95 per query, update, disk, RSS, parity mismatches against SQLite). Adapters: `sqlite` (reference) and `kuzu` (tag `kuzu`, the first candidate, kept so the decision can be re-checked). Adding a database = one adapter file and `go get` inside the nested module. `make bench-graphdb` runs it. Being built now; it does not block A-C.
