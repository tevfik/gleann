# gleann v1.9.0

This release improves how gleann finds code for natural-language questions,
fixes reranking in `gleann ask`, and adds ways to see why a result matched
and which sources an answer used.

Nothing changes in the index format, so no re-indexing is needed. Two
behaviour changes affect reranking users; see "Changed".

## Highlights

### Better answers to "how/where" questions: `--expand`

```bash
gleann search my-repo "how are search results deduplicated" --expand
gleann ask my-repo "how does sync detect deleted files?" --expand --expand-model qwen3.5:9b
```

Questions rarely use the words of the code that answers them. With
`--expand`, the language model first writes a short code sketch for the
question, in the main language of the index. gleann then searches with the
question and the sketch together.

On 121 questions about the gleann code base, with qwen3.5:9b on a GPU:

| | Right file first (R@1) | Right file in top 10 (R@10) | MRR |
|---|---|---|---|
| Before | 34% | 71% | 0.485 |
| `--expand` | **49%** | **81%** | **0.629** |

It costs one LLM call per new question (about 1.5–3 s on a GPU). Some
limits:

- **It needs a capable model.** With the 3B default chat model the gain was
  small, so set `expand_model` to a model of about 9B.
- **It is off by default.** On a machine without a GPU the LLM call usually
  costs more than it is worth.
- **Doc-comment-style queries** ("returns the …") lose slightly; combined
  with `--rerank`, no query set lost.
- **Identifier queries** (`LeannSearcher`, `parse_args`) are searched as
  typed.

The feature is also available as `"expand": true` on the REST search and
ask endpoints, as `expand` on the MCP `gleann_search` tool, and as the
`expand` / `expand_model` settings.

### A reranker that helps on code: `ms-marco-minilm-l6`

```bash
gleann models download ms-marco-minilm-l6
gleann search my-repo "where is the config file parsed" --rerank --rerank-model ms-marco-minilm-l6 --rerank-pool 20
```

On English code questions this model raised MRR by 0.07. The current
recommended multilingual model raised it by 0.01. The published GGUF of
this model is missing a layer, which makes its scores nearly constant.
gleann adds that layer from the original model while downloading (about
600 KB).

Reranking runs on the CPU, and its cost depends on the number of cores.
Times are per query, search included, with 20 candidates:

| Machine | Without reranking | With MiniLM-L6 |
|---|---|---|
| 1 core | 62 ms | 2.1 s |
| 2 cores | 62 ms | 1.1 s |
| 10+ cores | 62 ms | 0.4 s |

Reranking stays off by default. It is most useful for `ask` and for
agents, where a second per query is acceptable.

### See why a result matched: `--explain` and MCP `focus`

- `gleann search ... --explain` shows the parts of each result that matter
  most for the query, and how much each query word contributed (about
  70 ms per result).
- For agents, `focus: true` on the MCP `gleann_search` tool returns only the
  most relevant quarter of each result, about 4× fewer tokens.

### Which sources did the answer use: `ask --cite`

`gleann ask ... --cite` (REST: `"cite": true`) links each sentence of the
answer to the passage it came from and lists the sources used. It adds
about 100 ms and does not change the prompt. Treat the list as "sources
used", not as proof: an independent check found about 72% of the links
supported.

## Changed

- **Identifier queries are not reranked.** One-word or code-shaped queries
  keep their original order, because rerankers tend to push the exact
  symbol down.
- **`rerank_provider: ollama` now returns an error.** Ollama has no rerank
  API, and the previous fallback scored worse than no reranking. Use the
  built-in engine (`eif`), or `llamacpp` with a llama-server started with
  `--reranking`.
- `rerank_provider: llamacpp` now calls the `/v1/rerank` endpoint, so it
  needs a llama-server started with `--reranking`. Before, it compared
  embeddings, which did not help.
- `--rerank-pool` now limits only the candidates sent to the reranker; the
  first search stage keeps its full candidate lists.

## Fixed

- `gleann ask --rerank` and `gleann ask --graph` had no effect unless
  reranking or graph context was also enabled in the settings. Asking
  several indexes at once, or a project split into `<name>-code` and
  `<name>-docs`, never reranked, and neither did `gleann search --rerank`
  over several indexes. All of these now work. As a result, these commands
  are slower than before, because they now really rerank.
- `gleann ask` added the values of `--rerank-url`, `--rerank-pool` and
  `--rerank-provider` to the question text.
- The REST `ask` endpoint ran the search a second time to list its sources.
  It could then list passages the answer was not based on. It now reports
  the passages it used.
- `gleann bench` used the configured embedding model instead of the
  index's. When the two differed, every strategy silently fell back to
  keyword search.

## Upgrading

- **Settings:** no changes are needed.
- **Reranking with the `ollama` provider:** if `rerank_provider` is set to
  `ollama`, switch to `eif` (with a downloaded model) or to `llamacpp`.
- **Measurements:** the full set, including what was tried and left out,
  is in [docs/retrieval-experiments.md](../retrieval-experiments.md).
