# gleann v1.21.0

A security, filter-performance and consistency release. `GLEANN_TAGS` and
`X-Gleann-Target` now restrict every index route, including the write routes
and the OpenAI-compatible proxy, and no longer reveal which index names exist.
Filtered search uses on-demand SQLite expression indexes (RFC 010), which
halved the median latency of a filtered search in a paired 10K-vector run.
`gleann install` writes directives that fit every project and one
`SessionStart` hook instead of a hook on every file tool call, `gleann memory
context` is repository-scoped by default, and `--` ends flag parsing in `ask`
and `search`. On Windows, `PATCH /api/indexes/{name}` and file replacement no
longer fail under concurrent access, and the test suite no longer touches the
real home directory.

**Upgrade notes / behaviour changes.** Read these before upgrading a server
or an agent setup.

- **`GLEANN_TAGS` now restricts writes and the proxy.** `build`, `update`,
  `index-path`, `watch`, `upload`, `storage` and `DELETE
  /api/indexes/{name}` answer 403 for an index with another tag (before, they
  did not check it, and a `DELETE` of such an index removed it). The OpenAI
  proxy (`/v1/models`, `/v1/chat/completions`, `@tag` pseudo-models) lists and
  accepts only allowed indexes.
- **A missing index looks forbidden to a restricted client.** With
  `GLEANN_TAGS` set, a missing index answers exactly like a forbidden one
  (same status and body) on every index route. Unrestricted clients still get
  404.
- **Creating an index under `GLEANN_TAGS`.** A `build` may create a new index
  only when its `tags` include an allowed tag (the tags are stored with the
  index, so it stays visible); without one it is refused with 403. `upload`
  carries no tags and cannot create an index under `GLEANN_TAGS`.
- **Foreign tags are refused.** A restricted client may set only tags inside
  the allowed set on `build`, `PATCH` and `index-path`; any other tag, or a
  change that leaves none, answers 403. Requested tags are stored normalised
  (trimmed, no leading `@`).
- **`--` ends flag parsing in `ask` and `search`.** Everything after it is
  question text, verbatim: `ask idx -- --graph why` asks "--graph why", and
  `search idx -- why --index-dir /x` no longer changes the index directory.
- **`-h` as the value of a value-taking flag is not a help request** in all
  commands (`ask --model -h`, `search idx --kind -h`). `--help` after `--`
  stays text.
- **Status codes.** `PATCH /api/indexes/{name}` answers 403 for an index the
  client may not access and 404 for an unknown index (it answered 500).
  `DELETE /api/indexes/{name}` of a missing index is 404 (it answered 200).
  A corrupt index is no longer reported as "not found": `GET
  /api/indexes/{name}`, `search` and `ask` answer 404 (not found), 409 (old
  store format), 503 with `Retry-After` (busy, or a load cut short by the
  server's deadline) or 500 with a generic body (anything else).
- **`gleann memory context` is repository-scoped by default.** Without
  `--scope` it shows the global blocks plus the detected repository scope
  (outside a repository: the directory name). `--scope all` gives the old
  view of every repository. `GET /api/blocks/context` stays global.
- **Re-run `gleann install` to migrate.** It now writes new directives and a
  `SessionStart` hook (see Agent integration) and replaces what an older
  version wrote.
- **The graph post-commit hook needs a reinstall** (`gleann graph hook install`) to get the new script (see
  CLI).

**The one schema change is additive.** The first eq/in/exists filter search
on a meta key creates SQLite expression indexes (`passages_mf2_<hex(key)>`,
plus the companion index `passages_mfbad1`) in the index database. No
migration is needed and nothing has to be rebuilt. Older binaries keep the
indexes exact on write and never read them, so an index database that has them
still works with an older gleann. See
[docs/plans/010-filter-index.md](../plans/010-filter-index.md). Measured on 10K
x 384 vectors (HNSW, 1000 queries, k=10, 4 cores, 3 paired runs against
v1.20.2): the p50 of a 1% filter went from 13.3 to 6.9 ms and of a 10% filter
from 16.9 to 8.5 ms, with recall@10 unchanged (1.0000 and 0.9998 in both).
The index database grew by 12.9% with two filter keys and 19.1% with three.
Metadata writes cost more with indexes present (a bulk-write benchmark of 200
files x 20 passages took 255 ms with none, 357 ms with one, 371 ms with four
and 546 ms with sixteen).

## Security

- **`GLEANN_TAGS` no longer reveals which index names exist.** An index with
  another tag answered 403 but a missing index 404, so a restricted client
  could probe names. With `GLEANN_TAGS` set, a missing index now answers
  exactly like a forbidden one on every index route, including `POST
  /api/search` (whose 404 also carried the server's file path) and the
  OpenAI proxy. Unrestricted clients still get 404, without paths.
- **`GLEANN_TAGS` restricts the write routes and the OpenAI proxy too.**
  `build`, `update`, `index-path`, `watch`, `upload`, `storage` and `DELETE
  /api/indexes/{name}` never checked it; they now answer 403 before doing
  anything. A restricted client may only set tags inside the allowed set, so
  an index cannot be moved into, or created in, another tenant. The tags are
  part of the build's own metadata write, and a restricted create that fails
  is removed, so no untagged index is left behind that the client can neither
  see nor delete; the cleanup leaves an index that carries other tags
  (created by another tenant in between). A stored legacy `@x` tag matches
  `x`, so `["@Team"]` no longer locks a client out of its own index.
  `/v1/models` lists only the allowed indexes and `@tag` pseudo-models,
  `/v1/chat/completions` refuses (403) a model naming a disallowed or missing
  index, and an `@tag` model expands only to allowed indexes.
- **The tag check fails closed.** With `GLEANN_TAGS` set, an index whose
  metadata cannot be read is refused like a forbidden one (it used to pass
  the check and answer 409 or 500). The older `isIndexAccessible` gate, used
  by unified memory recall, graph ingest and the A2A search/ask/code skills,
  fails closed the same way (it treated a directory with corrupt or missing
  metadata as accessible, so graph relationships could be ingested into it).
- **`PATCH /api/indexes/{name}` enforces index access restrictions.** It
  applies the same `X-Gleann-Target` / `GLEANN_TAGS` check as `GET`, before
  the existence check, so a client restricted by `X-Gleann-Target` can
  neither modify nor probe other indexes. Under `GLEANN_TAGS` an index with
  another tag answers 403 and a missing one 404. A plain file named like the
  index answers 404, as `GET` does.
- OpenAPI, `docs/api.md` and `docs/env-vars.md` describe the new codes.

## Search & filters

- **On-demand metadata filter indexes (RFC 010).** The first eq/in/exists
  filter search on a meta key creates a SQLite expression index for it (up to
  16 keys per index database, on demand for indexes up to 200K passages;
  `EnsureFilterIndexes` for larger ones), so filtered searches no longer scan
  the whole passages table. Values SQLite and Go decode differently (numbers
  beyond float64, duplicate keys, non-UTF-8 bytes, a raw NUL byte after valid
  JSON) are verified by the filter engine. Numbers are under the upgrade
  notes.
- **Pre-selection of `source`/`file` filters** resolves the meta `source` key
  of passages stored without a source column.
- **Exact scoring of few filter matches** is no longer refused above 200K
  passages when a filter index can answer the pre-selection.
- **The table pass leaves metadata Go cannot decode to the engine.**
  Pre-selection no longer decides from meta text that SQLite reads and Go
  rejects (JSON5 forms, a BOM, a trailing form feed, a `"v\u0000"` key, a raw
  NUL byte): such rows go to the filter engine, so `exists:false` and the
  `file` fallback to the source column match what the engine returns. It
  also no longer disagrees with the engine on duplicate JSON keys and
  non-UTF-8 bytes, and a meta text of `null` no longer panics. This costs
  about 0.55 ms per 1,000 passages of a table pass (100K passages: +55-70 ms
  on 250-330 ms). Field names with U+FFFD or invalid UTF-8 are left to the
  engine.
- **Opening the embedding cache no longer lists the whole cache directory.**
  `NewCachedComputer` ran a glob over every file in the cache to remove temp
  files left by killed processes, on every CLI build, sync, search and server
  searcher load (about 580 ms at 200K entries, 1.4 s at 515K). The sweep now
  runs at most once an hour per directory (a `.stale-sweep` stamp file in the
  cache directory, shared by all processes) and reads names without a glob;
  opening a 200K-entry cache went from 580 ms to under 1 ms once swept (27 ms
  averaged over 5 opens including the one sweep, itself 135 ms instead of 580
  ms). Stale temp files (older than an hour) are still removed, in-flight
  writes are not.

## CLI

- **`gleann ask` honours `--`, and `ask` and `search` read no flag after
  it.** The shared config flags (`--model`, `--top-k`, `--index-dir`, ...)
  stopped at `--` nowhere before.
- **`--help` or `-h` as the value of a value-taking flag is not a help
  request** in `ask`, `chat`, `setup`, `service`, `graph <subcommand>`,
  `search`, `def`, `serve`, `agents`, `install`, `multimodal analyze` and
  `index build|rebuild|sync|watch|remove|tag|set|info|list|repair|migrate|
  storage`; each reads its own flag table, the one it already uses to reject
  unknown flags. `gleann benchmark --help` now prints the usage (it had no
  help check).
- **`gleann graph hook --help` prints the hook usage** instead of the general
  graph usage, and names the `GLEANN_GRAPH_INDEX` variable the hook needs. The
  installed post-commit hook now checks that variable first and stays silent
  when it is unset and never ends the hook early, so lines after it in
  `post-commit` still run (it used to print "rebuilding graph index..." and
  then do nothing). Reinstall the hook (`gleann graph hook install`) to get the new script.
- **`gleann ask --help` no longer presents `--classic` as a working flag.**
  It is a `gleann chat` flag; `ask` only tolerates it, and the usage says so.
- **`gleann index watch --quiet`** silences the status lines (start, initial
  sync, per-change updates, stop) and the embedded `llama-server` start, as
  `index build --quiet` and `index sync --quiet` do; errors and warnings stay
  on stderr. `--help` and `docs/configuration.md` list it.

## Server / API

- **A corrupt index no longer reads as "not found"** (status codes under the
  upgrade notes). The detail of a 500 goes to the log, not the response; a
  client that went away gets nothing (499 in the log). The OpenAPI response
  sets of these routes list the new codes.
- **`PATCH /api/indexes/{name}`** answers 404 for an unknown index instead of
  500 (detected with `errors.Is(err, fs.ErrNotExist)`), and `DELETE
  /api/indexes/{name}` of a missing index is 404, as the API spec says. The
  OpenAPI response set and `docs/api.md` follow.
- **Concurrent index metadata updates no longer fail or lose data.**
  `UpdateIndexMeta` serialises updates of one index and writes through a
  unique temporary file (previously parallel `PATCH`es shared one `.tmp` file
  and produced spurious 404/500 and lost updates). Temporary metadata files
  (`<name>.meta.json.<n>.tmp`) a crash left behind are deleted on the next
  update of that index once they are older than one hour.
- **A full build writes `<name>.meta.json` under the per-index metadata lock
  and through the same atomic temp-file replace as `UpdateIndexMeta`.** It
  was a plain `os.WriteFile`, so a `PATCH` or any reader during a build could
  see an empty or half-written file. The file mode is now always 0644, as
  `UpdateIndexMeta` already made it, instead of 0644 minus the umask.
- **A `PATCH` of description, tags, `mcp_exposed`, `auto_watch` or
  `source_dir` that lands while a rebuild runs is kept**, not overwritten
  with the values the rebuild read at its start: the build, `RebuildIndex`
  and the sync rebuild merge the file as it is now with their snapshot under
  the lock. A sync full rebuild also writes its first `meta.json` with the old
  index's tags, description, `mcp_exposed`, `auto_watch` and `source_dir` (it
  read them as unset until the end of the rebuild, so an index with
  `mcp_exposed=false` was exposed to MCP agents and missed by tag filters
  meanwhile).
- **`gleann serve` could return with the vault database still open.** The
  start-up task that prunes old upload records from `~/.gleann/vault/vault.db`
  was not tracked by the server's shutdown; `Stop` now waits for it (bounded
  by its context).
- **`Server.Stop` raced with `Server.Start`.** `gleann serve` stops the
  server from its signal handler while `Start` is still running, and both
  touched the HTTP server field without synchronisation (reported by the race
  detector). Set-up and shutdown are now ordered by a mutex; a stop during
  set-up makes `Start` return `http.ErrServerClosed`.

## Windows

- **`PATCH /api/indexes/{name}` no longer answers 500 under concurrent
  updates.** The handler does its read-modify-write in one locked
  `UpdateIndexMetaResult` (no pre-read and no re-read outside the per-index
  lock), index metadata reads retry the transient sharing errors
  (`internal/fsretry.ReadFile`), and a not-exist error from the metadata write
  is a 500 (`ErrIndexMetaWrite`), not a 404.
- **Replacing a file that is being read no longer fails.** `PATCH` (and any
  index metadata update), config, token, conversation and embedding-cache
  writes replace their file with `os.Rename`, which Windows refuses ("Access
  is denied" / sharing violation) while a reader still has the target open;
  they now go through `internal/fsretry`, a bounded retry (about 1 s, short
  backoff, Windows error codes only; a plain rename elsewhere). This was the
  cause of the CI failure of `TestPatchIndexConcurrent` (2 of 100 PATCHes
  answered 500).
- **More readers and renames ride out a transient sharing error.** Config,
  token store, admin token, TUI config and autosetup config reads use
  `fsretry.ReadFile`, and the database, vector-file and directory swaps in
  index migration, vector publication, sync rollback and memory migration use
  `fsretry.Rename` (identical to the plain call outside Windows).
- A server stopped right after start no longer leaves the vault database open
  (see Server / API), which showed as a failed removal of the home directory.

## Memory & TUI

- **`gleann memory context` without `--scope` no longer prints every
  repository's memory.** Its help already said "default detected repo" and
  MCP `memory_context` does that; the CLI used the unscoped window. This
  matters because the new Claude Code `SessionStart` hook runs it in every
  project.
- **A failed memory refresh is shown in the classic chat too, and once per
  failure run in both chats.** `gleann chat --classic` called the silent
  `memory.InjectRepoContext`; it now uses `InjectRepoContextErr` and adds a
  system line ("Memory not injected: ...") through the stream-start message,
  and the answer still runs. Both the classic chat and the agent chat (failed
  "memory" card) report the first failure only, and report again after a
  success is followed by a new failure, so a store that stays broken is no
  longer announced on every turn. The notice is shown again after `/new`,
  `/clear` or loading a conversation (the visible messages were cleared), and
  classic-chat answer tokens are no longer dropped when a system line lands
  after the streaming placeholder.
- **Agent chat TUI:** the context-window limit is read under the chat lock
  (data race with the background probe); the probe is cancelled and awaited
  when the chat exits; a failure to build the repository memory context is
  shown as a failed `memory` card instead of being dropped silently (the
  answer still runs). `memory.InjectRepoContextErr` reports the failure.

## Agent integration (`gleann install`)

- **Conditional directives and one `SessionStart` hook.** The user-level
  `~/.claude/CLAUDE.md` section used to apply to every project and told the
  agent to run `gleann graph report --index <name>` with a literal `<name>`;
  it now starts "When the current project has a gleann index ...", prefers
  the gleann MCP tools (`gleann_search`, `gleann_def`, `gleann_impact`,
  `gleann_graph_neighbors`, `gleann_read`, `gleann_sync`, `memory_*`) and lists
  the CLI commands as fallback; a project-level install names the index. No
  directive asks for a `GRAPH_REPORT.md` in the project root any more:
  `gleann graph map --index <name>` (stdout) is the overview and `graph report
  ... --output <path>` is optional. `graph query` is described as what it does
  (finds FQNs matching a pattern, then the BFS neighbourhood of the first
  match), `graph explain`/`callers`/`deps` take a fully qualified name, and
  the texts remind the agent to run `gleann index sync <name>` after editing
  code (also in AGENTS.md, GEMINI.md, the Cursor rule and SKILL.md).
- **The `PreToolUse` hook is replaced.** The hook on `Glob|Grep|Read|LS` ran
  `gleann memory list` before every file tool call. A `SessionStart` hook (10
  s timeout) now runs once per session: a hint when a `GRAPH_REPORT.md`
  exists plus `gleann memory context`, cut at 2000 bytes. Re-run `gleann
  install claude` to migrate.
- **No duplicated hooks and sections from an older version.** The Claude Code
  hook was recognised by its exact command text, so any other text (an older
  installer's `gleann memory list --json ... head -c 2000` variant, for
  example) was added again next to it. gleann hooks now end with the
  `# gleann-managed-hook v1` comment; install and uninstall remove every
  gleann-owned hook in `PreToolUse` and `SessionStart` (that marker, or the
  exact text of an older gleann hook) and print each one removed; any other
  hook, including one that merely mentions `gleann`, is kept.
- **Sections are replaced between their markers.** The `CLAUDE.md` and
  `GEMINI.md` sections are replaced between their `<!-- gleann ... -->`
  markers (every copy; a block with a missing or foreign end marker is left
  alone with a warning) instead of being skipped when an older variant is
  present. The AGENTS.md section has its own `<!-- gleann:agents -->` markers
  and one writer for all callers (`install`, `agents`, `setup`, `mcp`, `index
  build`); a marker-less older section is replaced only when it looks
  generated, and uninstall no longer deletes the user's later `## ...`
  sections (it used to cut to the next `---` or the end of the file) or leaves
  a `null` hook list behind.

## Tests & CI

- **Tests never touch the real home directory.** `internal/indexing`,
  `internal/multimodal` and `internal/vault` now run with a private `HOME`,
  and their `TestMain`s unset every `GLEANN_*_DIR`/`_DIRS` variable; a guard
  test fails if one points outside the private home.
  - `internal/indexing` built indexes against `$HOME/.gleann/cache/embeddings`
    with a new model name per run, so the directory grew without bound and
    every build scanned it for stale temp files (about 2 s per build at 500K
    entries under `-race`). `go test -race ./internal/indexing/` went from
    1166 s to 235 s on the same cores.
  - `internal/multimodal` and `internal/vault` created
    `~/.gleann/cache/multimodal` entries and `~/.gleann/vault`. A run of every
    test package with `HOME` pointed at an empty directory now leaves it empty
    (before: 1441 files from `internal/indexing`, 2 from
    `internal/multimodal`, 2 empty directories from `internal/vault`).
- **Sentinel job.** CI has a new Linux job, "Tests leave HOME empty"
  (`scripts/check-test-home.sh`), that runs the suite (`-short`, no race) with
  `HOME` and `USERPROFILE` at an empty directory and fails if a file appears
  in it (Go's telemetry under `.config/go` excepted).
- **Test hooks of `internal/metafault`** in the four metadata-fault tests
  fail only the path under test; the package has its own unit tests.
- **Windows path expectations.** The graph precision and install tests use
  Windows-safe path expectations.
- **CI timeouts.** The test step timeout is 40 minutes (it was 30) and the job
  timeout 60 (it was 45): the whole step took 29-32 minutes on macOS and
  Linux runners.

## Known limitations / follow-ups

- **Concurrent creates of the same name under `GLEANN_TAGS`.** The build holds
  no per-index lock around the existence and tag check, so two simultaneous
  creates of one name are not serialised.
- **A CLI rebuild racing a server `PATCH`.** The metadata merge under the lock
  covers rebuilds in the same process. A rebuild running in another process
  (`gleann index build` while `gleann serve` handles a `PATCH`) is not
  covered, because the in-process metadata lock is not shared; fixing it needs
  `PATCH` to take the cross-process index lock.
- **RFC 008 step 0b (one retrieval service, `internal/retrieval`) is not in
  this release.** The work in progress is parked.
- **Windows: a heap copy per open index.** The vector file is replaced with a
  rename while a cached searcher may still serve the old generation, which
  Windows refuses for a file that is open or mapped; the Windows code copies
  the file to the heap instead of mapping it. Per-generation vector files
  would remove the copy and need an RFC.
