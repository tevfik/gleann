# gleann v1.20.0

This is a breaking release. Every index is now one SQLite database, the
code graph lives in it and works in every build, and the embedded Kùzu
graph database is gone. Indexes built by gleann v1.9 or earlier must be
converted once with `gleann index migrate`; nothing is re-embedded.

In short:

- **One store per index.** `<IndexDir>/<name>/<name>.db` holds the
  passages, the persisted FTS5 lexical index, the file manifest, the code
  graph and the document graph, and they change together, one transaction
  per source file.
- **A code graph in every build**, including `go install`,
  `CGO_ENABLED=0` and Windows. `-tags treesitter` now only adds the
  tree-sitter parsers (calls in languages other than Go).
- **Incremental vector updates.** A one-file `index sync` at 100K passages
  takes about 0.3 s instead of the 73 s a full vector rewrite took.
- **Memory** moves to SQLite (`memory.sqlite`), so several agent processes
  can write it at once.

Read "Breaking changes" and "Upgrading" before you install it.

## Breaking changes

- **Format 2 is the only index format.** The old store format of v1.9 and
  earlier (bbolt `<name>.passages.db`, `<name>.lex.db`, Kùzu
  `<name>_graph`) is not read. Search, ask, chat, sync, watch, info,
  repair, storage, tag, set, build, the graph commands, REST, MCP and A2A
  stop on such an index with:

  ```
  index X uses the old store format; run: gleann index migrate X
  ```

  `gleann index list` marks old indexes; `gleann index remove` and
  `gleann index rebuild` still work on them.
- **Removed environment variables:** `GLEANN_STORE_FORMAT`,
  `GLEANN_LEXICAL` and `GLEANN_LEXICAL_OPTS` (format 2 and FTS5 with
  AND-first queries and a document-frequency cut of 0.2 are fixed). A
  value that is still set is ignored, and every command prints one line:
  `notice: <names> ignored: removed in gleann v1.20 (every index is format 2 with FTS5 lexical search)`.
  `GLEANN_KUZU_AUTOREPAIR` is gone too.
- **Kùzu is removed.** gleann no longer depends on `go-kuzu` or `libkuzu`,
  and the full build ships no `libkuzu`. An old `<name>_graph` directory is
  never read; `gleann index migrate` rebuilds the graph from the index's
  source directory.
- **Raw Cypher is removed.** `POST /api/graph/{name}/query` with
  `type: "cypher"` answers 400
  (`raw Cypher was removed; use callers/callees/symbols_in_file/impact`),
  and the web UI's "Raw Cypher" option is gone. The typed queries remain,
  and `gleann graph export --format cypher` still writes Neo4j statements
  for use in another tool.
- **`gleann index migrate`** lost `--rollback` and `--language`. The old
  files stay next to the index until you run it with `--cleanup`.
- **MCP graph tools are always advertised.** `gleann_graph_neighbors`,
  `gleann_impact`, `gleann_document_links`, `gleann_graph_stats`,
  `gleann_symbols_in_file`, `gleann_document_toc` and the analysis tools
  (`gleann_communities`, `gleann_risk_analysis`, `gleann_repo_map`,
  `gleann_navigate_symbol`) are listed and work in every build. An index
  built without `--graph` answers
  `index "X" has no code graph yet; build it with: gleann index build X --docs <dir> --graph`.
- **`GET /api/graph/{name}`** of an index without a code graph is 404
  (it answered `available: true` with zeros), and `toc` of a path that is
  not an indexed document is 404 (it was a 500). The `module` field of
  `POST /api/graph/{name}/index` is accepted and ignored.
- **Memory is in SQLite.** The first open copies `memory.db` to
  `memory.sqlite` and keeps the old file as `memory.db.v1`. After that,
  older gleann binaries on the same machine get an error on memory
  commands: **update every installation together.**
- **The REST server indexes or reads directories on a client's request
  only inside `allowed_roots`** (setting or `GLEANN_ALLOWED_ROOTS`; default:
  your home directory), otherwise it answers 403. Servers that index
  directories outside the home directory through the API need
  `allowed_roots` set. The command line is not restricted.

## Why

We measured Kùzu against a SQLite code graph on the same synthetic graph
with 1M CALLS edges. SQLite gave the same answers and was 15 to 175 times
faster on graph queries and 6 times faster on a one-file update. Kùzu
also needed CGo and a shipped shared library, so the default build and
Windows had no code graph at all. Keeping everything in one SQLite file
also gives passages, lexical index and graph one transaction. The full
reasoning, the numbers before and after the SQLite schema rework, the
parity checks and how to evaluate another database later are in
[docs/decisions/kuzu-to-sqlite.md](../decisions/kuzu-to-sqlite.md).

## Upgrading

1. **Install v1.20.0 everywhere on the machine** (CLI, server, MCP
   configurations, editors' gleann). Memory is converted on first open,
   and old binaries cannot read it afterwards.
2. **See which indexes need converting:**

   ```bash
   gleann index list        # marks indexes in the old store format
   ```

3. **Convert them.** Vectors are reused, so nothing is re-embedded. Passage
   IDs with gaps are renumbered, the lexical index is rebuilt, a
   `<name>_memory_vectors` index is converted too, and the code graph is
   rebuilt from the index's source directory when the old index had one:

   ```bash
   gleann index migrate my-code          # one index
   gleann index migrate --all            # every index
   gleann index migrate my-docs --graph  # also build a graph the old index did not have
   ```

   When an index has gaps in its passage IDs and its vectors cannot be read
   back (pruned embeddings, `recompute` storage mode), migrate stops and
   points you to `gleann index rebuild`.
   `gleann index rebuild <name>` also works for any index: it re-embeds,
   and it takes the source directory, tags, description, MCP exposure,
   model, backend and graph setting from the index, so `--docs` is no longer
   needed.
4. **Check and clean up.** The old files (`<name>.passages.db`,
   `<name>.lex.db`, `<name>_graph`, `<name>_graph_file_hashes.db`, ...)
   are never deleted implicitly:

   ```bash
   gleann doctor                         # lists leftovers and unimported memory stores
   gleann index migrate my-code --cleanup   # deletes the old files, printing each path
   ```

5. **Memory entities stored by v1.9** (`inject_knowledge_graph`, kept in
   `<IndexDir>/<name>_memory`, a Kùzu store) cannot be rebuilt from
   sources. Carry them over once with the separate export tool, released
   as `kuzu-memory-export-v1.20.0-<os>-<arch>.tar.gz` for linux-amd64,
   linux-arm64 and darwin-arm64 (binary plus the Kùzu library; keep them
   in one folder), or built with `make kuzu-memory-export`:

   ```bash
   kuzu-memory-export -o gleann-memory-export ~/.gleann/indexes   # every *_memory store
   gleann memory import-graph gleann-memory-export                # a file or the folder
   ```

   The tool opens the stores read-only. The import keeps ids,
   attributes, timestamps and the archive, and a second run changes
   nothing. Until a store is imported, the server and the MCP server log
   the two commands once per process and `gleann doctor` lists it. See
   [docs/memory_engine.md](../memory_engine.md#upgrading-entities-from-v19).
6. **Remove stale environment variables** (`GLEANN_STORE_FORMAT`,
   `GLEANN_LEXICAL`, `GLEANN_LEXICAL_OPTS`, `GLEANN_KUZU_AUTOREPAIR`) from
   shell profiles, service files and MCP configurations; the notice tells
   you which are still set.

`gleann index migrate` is the only code in v1.20 that reads the old format.
It stays for v1.20.x and is removed in v1.21, together with the memory
entity import path.

## Highlights

### A code graph in every build

`gleann index build <name> --docs <dir> --graph` and `index sync` write
the code graph into the index database, one transaction per changed file,
and `gleann graph deps|callers|explain|path|query|toc|viz|report|communities|export|wiki|hook|map|risk`,
the MCP graph tools, the REST `/api/graph/*` endpoints and the A2A skills
read it in every build. Without tree-sitter, Go files get CALLS,
IMPLEMENTS and REFERENCES edges from `go/ast` (and from `go/types` when
the module type-checks); other languages contribute their declarations.
With `-tags treesitter` (the `full` release), Python, JavaScript,
TypeScript, Rust, Java, C, C++, C#, Ruby, PHP and Swift files get calls
too. Community detection, PageRank, risk, the repo map, export and viz
are now deterministic: the same graph gives the same output every run.

Synthetic graph with 1M CALLS edges, p50, cores 0-3 (`bench/graphdb`):

| | Kùzu (v1.9) | SQLite (v1.20.0) |
|---|---:|---:|
| callers, depth 3 | 125 ms | 0.71 ms |
| impact, depth 3 | 298 ms | 0.73 ms |
| symbol search | 34.5 ms | 1.47 ms |
| shortest path | 0.43 s, found no path (node cap) | 2.61 ms |
| one-file update | 865 ms | 102 ms |
| full load | 2.3 s | 3.77 s |
| disk | 52 MiB | 75.3 MiB |

On this repository (12,224 symbols, 35,620 edges) a full graph build
takes 0.85 s and the graph tables 7.8 MiB. A graph created by a
development build before the final schema is converted in place on first
open (7 s at 1M edges).

### Incremental vector updates

A sync no longer rewrites the vector index. New passages go to a small
exact-search delta file next to it, removed ones become dead slots, and a
merge or compaction rebuilds the index from the stored vectors (no
re-embedding of unchanged text) once the delta passes max(4096, 2 %) of
the passages or 5 % of the slots are dead. Running servers and MCP
sessions pick up the change without a reload.

At 100K passages:

| `index sync` of | Time |
|---|---:|
| one added file | 0.349 s |
| one changed file | 0.334 s |
| one deleted file | 0.320 s |
| nothing changed | 0.087 s |
| one file, rewriting the vector index (format 2 before RFC 005) | 73 s |

Search quality does not drift with repeated updates: after 50 rounds of
updates, recall@10 was 0.941 against 0.917 for a fresh build of the same
data.

### Faster cold starts with the persisted lexical index

The lexical (BM25) leg is an FTS5 index on disk instead of an in-memory
index rebuilt on every cold open. At 100K passages the first query of a
running server went from 4.5 s to 0.3 s and its memory from 1.2 GB to
0.4 GB; at 1M passages warm search p50 went from 0.9 s to 47 ms, the
first server query from 35 s to 3.6 s, server memory from 8.8 to 1.4 GB
and the index from 2.46 to 1.97 GiB. Builds take about 10-18 % longer.

### Memory

- **SQLite memory store**, safe for several writers at once; the memory
  entity graph (`inject_knowledge_graph`, `delete_graph_entity`,
  `traverse_knowledge_graph`, `/api/memory/*`) is in it too and works in
  every build. The memory vector syncer (`<name>_memory_vectors`) also
  runs in every build.
- **Token budget** for the injected `<memory_context>` (4000 estimated
  tokens by default, `GLEANN_MEMORY_MAX_TOKENS`); whole blocks are dropped
  lowest priority first, never truncated.
- **Ranked memory search** (BM25 over label, content, tags, paths and
  symbols).
- **Failure memory:** `gleann memory failure add` and MCP
  `memory_failure_add` record a failed command and the fix that worked;
  `memory context --command … --path …` brings matching failures back.
- **Markdown export and import** (`gleann memory export|import --dir`) and
  `gleann memory reflect [--dry-run] [--revert <run-id>]`.

### Proxy and server

- `X-Gleann-Hybrid-Alpha` sets the vector/lexical weight per request (0 =
  lexical only) in both proxy modes.
- `X-Gleann-Cover` (or `proxy_cover`) keeps the best passage of every index
  that is close to the overall best in multi-index pass-through answers.
  The default margins are starting points, not calibrated to a model.
- The pass-through context intro is configurable (`proxy_context_intro`,
  `GLEANN_PROXY_CONTEXT_INTRO`) and always asks the model to answer in the
  language of the question.
- `GET /api/storage` also reports the whole data folder (`data_dir`,
  `data_bytes`, `data_folders`).
- The HTTP write timeout follows the build limit
  (`max(30 min, GLEANN_TIMEOUT_BUILD_S + 5 min)`), so long builds keep
  their answer.
- Uploaded documents leave no trace outside their index.
- In the in-process `eif` embedder a search no longer waits behind a
  build: embedding one query while a build batch runs took 12 ms instead
  of 3.7 s (multilingual-e5-small q8_0, linux/amd64, 16 cores).

### Search

- **Filtered search returns k results**: the candidate pool widens until
  k results pass the metadata filter (capped at 4096), then falls back to
  pre-selecting the matching IDs in SQL.
- **float16 HNSW vectors** (`hnsw_config.vector_dtype: f16`,
  `GLEANN_HNSW_DTYPE=f16`): on 100K × 768 vectors the index file went from
  315 to 169 MB with recall@10 unchanged.
- **DiskANN memory-maps its vectors**, and `searcher_cache_budget` caps the
  memory of cached searchers in `serve` and the MCP server.

## Security

- The REST server confines client-requested paths to `allowed_roots` (see
  Breaking changes); MCP file tools stay inside the project and the
  exposed indexes' source directories.
- Plugins get a per-plugin bearer token (`GLEANN_PLUGIN_TOKEN`), sent on
  every request except `/health`.
- `/api/proxy/models` no longer follows client-supplied loopback, private
  or link-local hosts (`GLEANN_MODEL_DOWNLOAD_ALLOW_PRIVATE=1` lifts it).

## New settings

| Setting | Default | Meaning |
|---|---|---|
| `GLEANN_DELTA_MIN` / `GLEANN_DELTA_SHARE` | 4096 / 0.02 | Size of the vector delta file that triggers a merge |
| `GLEANN_DEAD_SHARE` / `GLEANN_DEAD_SHARE_PRUNED` / `GLEANN_DEAD_MIN` | 0.05 / 0.05 / 256 | Share and minimum count of dead vector slots that trigger a compaction; an explicit `GLEANN_DEAD_SHARE` sets the minimum to 0 |
| `allowed_roots` / `GLEANN_ALLOWED_ROOTS` | home directory | Where the REST server may index or read on a client's request |
| `GLEANN_MEMORY_MAX_TOKENS` | 4000 | Memory injection budget (0 = unlimited) |
| `searcher_cache_budget` / `GLEANN_SEARCHER_CACHE_BUDGET` | 0 | Memory budget of cached searchers |
| `use_mmap` / `GLEANN_MMAP` | unset | Memory-map the vector index for every backend |
| `proxy_cover`, `proxy_context_intro` | off, English intro | See "Proxy and server" |

All variables are listed in [docs/env-vars.md](../env-vars.md).

## Also fixed

- `go install github.com/tevfik/gleann/cmd/gleann@latest` works.
- A malformed `~/.gleann/config.json` stops commands with the file, line
  and column instead of being ignored.
- Every command rejects unknown flags (exit code 2, with a suggestion),
  and `--flag=value` works like `--flag value`.
- `index sync` no longer deletes the only good copy of an index after a
  killed rebuild, and `index watch` updates go through the same path as
  `index sync`.
- One build or sync per index across processes (index lock
  `<IndexDir>/<name>.lock`); a second process stops at once with a message.
- The text chunker splits text without sentence punctuation or spaces
  (logs, minified text, CJK) at the size limit.

The full list is in [CHANGELOG.md](../../CHANGELOG.md).

## Measured quality

The retrieval-quality gate (`internal/quality`, 141 tasks over a pinned
snapshot of the repository) moves to the FTS5 numbers:

| MRR | v1.9 (in-memory BM25) | v1.20.0 (FTS5, AND-first, df 0.2) |
|---|---:|---:|
| BM25 | 0.530 | 0.521 |
| Dense | 0.297 | 0.297 |
| Hybrid | 0.381 | 0.376 |

The loss of 0.009 (BM25) and 0.005 (hybrid) is accepted for the faster
cold starts and the lower latency tail.

## Known limits

- **Merge and compaction cost about as much as a build without
  embeddings:** at 100K passages 109.6 s and 110.3 s against 126.2 s for a
  full build (with a 0 ms test embedder); they save only the embedding
  calls. They run when the delta or the dead share passes its threshold,
  not on every sync. Faiss and pruned (`recompute`) indexes cannot return
  their stored vectors, so they take the full re-embedding path instead.
- **Incremental updates at 1M passages** are not measured yet; the 100K
  numbers above are.
- **Call graph languages** (tree-sitter builds): Lua gets declarations
  only; Ruby calls are found only with parentheses; Elixir records `def`
  and `defmodule` as calls; Kotlin calls are charged to a per-file
  `<script:file>` symbol; Scala call extraction is not covered by a test.
  See [docs/treesitter.md](../treesitter.md#call-graph-limits).
- **No `kuzu-memory-export` for Windows**: gleann never had a Kùzu build
  for Windows, so there are no v1.9 Windows stores to export.
- **The `eif` query lane** is measured on linux/amd64 only.
- **Old v1.9 memory traverse answer:** one v1.9.0 `traverse_knowledge_graph`
  answer is not reproduced after import because v1.9 returned an edge the
  store does not contain; see
  [docs/memory_engine.md](../memory_engine.md#upgrading-entities-from-v19).
